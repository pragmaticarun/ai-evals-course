## 8. Risks and caveats

- **Synthetic data.** Every model turn in the fixtures was generated by Claude subagents. The method transfers; the rates do not. Re-record live (module 12, *Make it your own*) before using any number for a real decision.
- **Sample size.** 119 dev queries detect a paired change of about 0.11; the drm-resolution slice (14 queries) cannot detect anything smaller than its discordant share. A change can be detected below that size only when almost every query that changed moved the same way: the best rejected configuration's difference, +0.059 [+0.000, +0.118], rests on 10 fixed and 3 broken queries.
- **The rejections.** `v3`, the best rejected configuration, failed its pre-registered rule (CI lower bound +0.008 > 0; guardrail: p95 14.8 s > 12 s; cost/success $0.0118 > $0.01). Against its parent `v2` it changed 14 queries, exact McNemar p = 0.06. A rejection means the rule did not show an improvement within the guardrails, not that there is none; a larger study could still find one.
- **Judge error.** The self-check judge fails 6 good first answers and passes 3 of the 3 bad ones on dev. RAG faithfulness has a lower TNR than TPR (section 6), so raw judge pass rates overstate quality. The TNR of `tool-grounding`, `false-premise`, `next-step` and RAG answer relevance is n/a (0/0): their validation labels hold no failing answers, so how often they pass bad ones is unmeasured.
- **Metric definitions differ across modules.** Module 6 grades all human-labelled failure modes (v1 → v2 +0.000 [-0.034, +0.034]); module 11 grades four checks (v1 → v2 -0.008 [-0.067, +0.050]). They answer different questions; do not quote one as the other.
- **Modes module 11 does not track.** Its labels cover four modes. Fabricated evidence, wrong tool arguments, wrong API details, and retrieval misses (modules 3 and 7) were not re-measured for any configuration. Module 3's failing traces show `fabricated-evidence`, so the mode the error analysis found is among the unmeasured ones.
- **Distribution shift.** Production traffic after the 4.2.0 rollout differs from the dev set (more AV1, a new device); the dev results say nothing about it.
- **Guardrails.** `v1`, the release configuration, is already over the pre-registered guardrails on dev (p95 15.8 s > 12 s; cost/success $0.0103 > $0.01; p95 upper CI 30.4 s), so any change must bring these down, not only hold them.
- **Security.** Guardrails v2 still let 2 of 60 attacks through (against 1 with no guardrails) and refuse 9 of 60 benign requests; the suite has 60 cases, so a 0% observed rate would still allow an upper bound near 6%.
