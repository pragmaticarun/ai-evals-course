# 3. Error analysis

**Goal:** read traces systematically and turn what you see into a ranked list of failure modes.

**Estimated time:** 7 hours (lesson 1.5 h, lab 4 h, exercises and quiz 1.5 h)

By the end of this module you will be able to:

- review a trace in a fixed order and write a short, specific note about the first thing that went wrong
  (*open coding*);
- group those notes into failure modes with definitions someone else could apply (*axial coding*);
- tell apart tool-call errors, retrieval misses, and failures that compound over several steps;
- count and rank failure modes by how often they happen, how much they hurt, and how easy they are to fix;
- decide when you have read enough (*saturation*) and who should be doing the reading.

Artifacts: your annotation file (`runs/m3_labels.csv`), failure taxonomy sheet v1 (`runs/taxonomy.csv`), and a
Pareto chart (`runs/pareto.svg`).

## Intuition: triage before you fix

If you have worked on an Android app at scale, you have done this already. A crash dashboard with 4,000 reports
is useless until it is grouped by signature: *these 1,900 are the same `IllegalStateException` in the player
release path, these 300 are the OEM codec bug on one chipset*. Once grouped and counted, the next week's work is
obvious. Nobody fixes crashes in the order they arrived, and nobody decides the buckets before seeing the reports.

Error analysis is that triage for an LLM agent, with one difference: agent failures have no stack trace. An answer
that confidently names the wrong decoder looks exactly like an answer that names the right one. A person who knows
the domain has to read the trace and say what went wrong. So the work is:

1. **Look** at a sample of real (or realistic) traces, one at a time.
2. **Write down** what went wrong in each, in plain words. No categories yet.
3. **Group** the notes into a small set of named failure modes.
4. **Count** them and decide what to fix first.

The order matters. Teams that start from a generic list ("hallucination", "helpfulness", "toxicity") measure things
that may not be their problem and miss things that are. In the MediaDoctor traces below, the one failure the
reviewer found is the agent adding a *specific detail that no tool returned* (a timestamp, another device's decoder
limits) to an otherwise correct answer. "Hallucination" would cover it, but would not tell you that the tools ran
fine, that the citations are real, and that the problem is one extra sentence. The categories have to come out of
the traces.

This approach, including the open and axial coding vocabulary borrowed from qualitative research, is the core of
Hamel Husain and Shreya Shankar's teaching on evals; see [Credits](../../credits.md) for where to read it in their
own words.

## Step 1: read each trace the same way

Reading 100 traces sounds slow. It is about two hours if every trace is read in the same order and you write one
line per trace. The lab's review layout shows a trace like this:

```text
case m3t088   trace 56c920e2a750   2 model calls   $0.0069
Q: [MD-4188] Our live channel errors out if the app sat in the background ~10 min. Log in live_resume.txt.

  [1] chat:plan                 in=629 out=93
  [2] execute_tool logcat_grep  args={"log": "live_resume.txt", "pattern": "error|exception|expired|403|401|token|resume"}  ->  {"log": ..., "matches": 7, "lines": ["L2: 11-21 09:26:40.017 ...
  [3] execute_tool search_kb    args={"query": "live stream resume background expired token manifest"}  ->  {"results": [{"id": "behind-live-window", ...
  [4] retrieval                 query='live stream resume background expired token manifest' k=2 -> ['behind-live-window', 'av-sync']
  [5] chat:answer               in=1412 out=193

Answer:
  Likely cause: The app was paused at 09:15:02 and resumed at 09:26:40; on resume ExoPlayer raised `BehindLiveWindowException` ...
  After roughly 11 minutes in the background the segments it needed had left the live stream's sliding window ...
  Next step: In `Player.Listener.onPlayerError`, check for `ERROR_CODE_BEHIND_LIVE_WINDOW`, then call `player.seekToDefaultPosition()` ...
  Sources: [tool:logcat_grep] [kb:behind-live-window]
```

A reading order that works:

1. **Question, then answer.** Would you, as the expert, accept this answer? Decide *pass* or *fail*, nothing in
   between. A binary verdict forces a decision; a 1 to 5 score lets you avoid one.
2. **If it fails, walk the steps from the top** and stop at the first step whose output is wrong: a bad tool
   argument, an error nobody handled, irrelevant documents, or a final answer that does not follow from what the
   tools returned. That is the **first upstream failure**.
3. **Write one line** about what you saw. Then move on.

Here the diagnosis and the fix are *correct*, and both sources are real. But the answer opens with a pause time,
09:15:02, and "roughly 11 minutes in the background". The grep in step 2 returned lines L2 to L9 of the log; the
`onPause` line, L1, did not match its pattern, so the agent never saw that timestamp. The tool call and the
retrieval are fine. The first thing that went wrong is step 5, the final answer, which states a fact no tool
returned. Compare `m3t080`, the same question with a grep pattern that includes `background`: there L1 is in the
tool output, and the same sentence is grounded. Only reading the tool output next to the answer tells the two apart.

!!! tip "Pass the obvious, fail the specific"
    Spend your time on failures. If an answer is right, grounded, and useful, mark it pass and move on in seconds.
    If you cannot decide, it is usually a fail with a note saying what bothered you.

## Step 2: open coding

**Open coding** means writing free-text notes about each failing trace, in your own words, without forcing them into
categories. Good notes are:

| Good note | Weak note | Why |
|---|---|---|
| says app paused at 09:15:02, ~11 min in background; grep returned L2 to L9, not the onPause line L1 | hallucination | Says *what* is wrong and *where the evidence is* (or is not). "Hallucination" is a conclusion, and covers several different problems. |
| next step says lumen-l3 does H.264/HEVC hardware decode to 1080p60; only codec_caps for video/av01 was called | made something up | Names the claim and the call that would have been needed, which points at the fix. |
| answer about atlas-a1 adds that lumen-l3 has a 1080p30 software AV1 decoder; no tool queried lumen-l3 | wrong | Names the step (the answer) and shows the rest of the answer was fine. |
| search_kb('sound continues when phone rings') returned av-sync, not audio-focus | bad retrieval | Records the query and the result, so you can later tell a query problem from a retriever problem. (A hypothetical: this set has no retrieval misses.) |

Three habits keep notes useful. Note **what you observed, not the fix** (the fix comes later, and often is not what
you expect). Note the **first** failure, and mention later ones only if they are independent. And **do not look at
the reference labels** until you have done your own pass; the point is to see what *you* see.

## Step 3: axial coding

Once you have your notes (on most systems, 30 to 50 failing traces), read them all together and group them. This
is **axial coding**: you look for notes that describe the same underlying problem, give each group a name, and write
a one-sentence definition that someone new could apply to a trace without asking you.

On this set there are only three failure notes, all from the reference, and they group into one mode:

| Trace | Note (open code, shortened) | Failure mode (axial code) |
|---|---|---|
| `m3t010` | core answer about atlas-a1 is right, but it states lumen-l3 has only a software AV1 decoder capped at 1080p30; no tool queried lumen-l3 | fabricated-evidence |
| `m3t072` | cause is right, but the next step claims lumen-l3 supports H.264/HEVC hardware decode up to 1080p60; no avc/hevc codec_caps call was made | fabricated-evidence |
| `m3t088` | cause and fix are right, but the answer states the app was paused at 09:15:02 and ~11 minutes in the background; the grep did not return the onPause line | fabricated-evidence |

Three topics (AV1 shipping, AV1 frame drops, live-stream resume), one behaviour: a correct answer with one added
detail that no successful tool returned. The first 30 traces contain only one of them (`m3t010`); on a set with
more failures you would expect several groups by this point.

The reference definitions file, `data/labels/module03_modes.toml`, defines **nine** modes. Only
*fabricated-evidence* occurs in the current labels. The other eight (ignored-tool-output, wrong-tool-args,
wrong-api-detail, retrieval-miss, skipped-investigation, redundant-steps, vague-next-step, format-violation) are
common agent failures that this agent did not show on these 100 questions. Keeping such definitions ready is fine;
counting them before you have seen them is not.

Decisions you will face while grouping:

- **Split or merge?** Split when the fix (or the detector) differs. The reference definition of
  *fabricated-evidence* covers both "cites a tool whose call failed or never happened" and "quotes details that no
  successful tool returned". The first is caught by a simple citation check; the three traces here are all the
  second kind, which that check cannot see (see the signals section below). If you expect to measure them
  differently, two modes may serve you better than one.
- **Name the behaviour, not the topic.** "Live-stream problems" is a topic; failures inside it differ.
  *fabricated-evidence* covers AV1 decoding and live-stream resume alike.
- **Write the definition before you count.** If you cannot write one sentence that separates two modes, merge them.
- **Expect the definitions to change.** Reading more traces sharpens what you think "wrong" means. Shankar and
  co-authors call this *criteria drift*: graders' criteria shift as they see outputs. Re-label earlier traces when
  a definition moves.

An LLM can help here by proposing groupings of your notes, but treat its output as a suggestion: you know which
differences matter for the fix.

The result is a definitions file, `data/labels/module03_modes.toml` in the reference, with a severity, a fixability,
and an expected detector for each mode. Module 5 turns the top modes into evaluators; the `detector` field is your
first guess at which ones a code check can catch and which need a judge.

## Three kinds of failure worth special attention

### Tool-call errors

Not every tool error is a failure. The `errors` command lists every failed tool call and sorts what happened next
into three outcomes:

| What happened after the error | Usual verdict |
|---|---|
| Retried with the right name and continued (`recovered`) | **pass**, if the answer is right: the error message listed valid names and the agent used it |
| Gave up and hedged ("I could not inspect ..., so this is a guess") (`gave up`) | fail: wrong-tool-args |
| Cited the tool anyway, as if it had worked (`cited anyway`) | fail: wrong-tool-args *and* fabricated-evidence |

On this set the command reports **0 failed tool calls**: in all 100 traces the agent used file, device, and log
names that exist. That is worth knowing in itself (the tools' names and error messages are not a problem today),
but it means this section has nothing to sort. On a set where errors do occur, look at the arguments: if they
cluster on near-miss names (`late_moov.mp4` for `progressive_late_moov.mp4`), the tool, not the model, is the
cheapest place to act (accept unambiguous near-misses, or return a "did you mean" in the error).

### Retrieval misses

The `retrieval` command checks each `search_kb` call against the document the case needs. On this set **53 of 53**
retrievals return it (the agent searched in 86 traces; 53 of those searches are on cases that name the document
they need, and every one of them found it). The agent's queries are mostly built from the terms of the problem (`'audio focus phone call
pause playback'`, `'Widevine security level L1 L3 HD'`), which suits the naive keyword retriever. A miss would look
like a query such as `'sound continues when phone rings'`, which matches nothing about audio focus and returns the
A/V sync note, and an answer that follows the wrong document.

When you see a miss, ask one question: **would a better query have found the document?** If yes, the problem is
query formulation (the model's step, fixable by prompt or query rewriting). If no, it is the retriever or the
knowledge base (coverage, ranking, chunking), which module 7 measures properly. Record which one in your note.

### Compounding failures

In a multi-step trace, one early mistake can produce several visible symptoms: a tool called with a wrong device
name fails, and the answer then states that device's decoder limits as if it had read them. Two modes apply
(*wrong-tool-args* and *fabricated-evidence*), but there is one first upstream failure: the tool call. Record the
first failure in `first_upstream`, and tag independent failures too. Fixing upstream often removes downstream
symptoms, so the `first_upstream` counts tell you *where* in the pipeline to work. On this set:

| First upstream step | Failing traces |
|---|---|
| `chat:answer` (the final answer goes beyond good evidence) | 3 |

No failure here compounds: in all three, every earlier step was fine and the problem starts in the final answer. On
a set with more failures you would expect rows for `chat:plan` (skipped or redundant tool calls), `retrieval`, and
`execute_tool ...` (bad arguments) as well, and their relative sizes would tell you whether to work on the prompt,
the retriever, or the tools.

Multi-step traces can also fail on cost rather than correctness. Not here: every trace makes exactly 2 model calls
and at most one search, and the failing traces cost $0.0059 on average against $0.0063 for passing ones. Cost does
not point to these failures; reading does.

## Step 4: count and prioritise

With every failing trace coded, count how many traces show each mode (a trace with two modes counts once for each).
The reference result for all 100 traces:

| # | Failure mode | Traces | Severity | Priority (traces × severity) | Fixability | Most common first upstream |
|---|---|---|---|---|---|---|
| 1 | fabricated-evidence | 3 | 3 | 9 | easy | chat:answer |

3 of 100 traces fail. `rank` lists only modes that occur, so the eight unused definitions do not appear. With one
mode there is nothing to prioritise between, but the reading rules are the ones you will need on a larger set:

- **Frequency alone is not priority.** A wrong decoder claim sends an engineer down the wrong path for a day; a
  missing `Sources:` line costs nobody anything. Severity (1 annoying, 2 misleading or costly, 3 harmful or
  trust-breaking) is a judgement call, which is why the domain expert makes it.
- **Check that the fixability and detector fit the traces you have.** The reference marks *fabricated-evidence* as
  easy, with a code detector, because its usual form (citing a tool that failed or never ran) is caught by the
  module 2 citation check. None of these three is that form: every cited tool did run, and the made-up part is a
  detail inside a sentence. The citation check flags none of them (see the signals section). Measuring this form
  needs an LLM judge (module 5) or a narrow rule per kind of claim (exercise 3 shows how narrow such rules are).
- **Read the shape of the Pareto chart.** Here it is a single bar at 100%. On a young agent with many separate
  problems it is often flat (the top three modes covering half the failures, not 80%); then severity and fixability
  decide. When one bar towers, frequency does.

The priority formula is deliberately simple. Some teams use count × severity ÷ effort, or weight by how many users
ask that kind of question. Whatever you use, write it down in the taxonomy sheet so the ranking can be argued with.

## When to stop: saturation

You stop reading when new traces stop teaching you anything: no new failure modes and no changes to the definitions.
Qualitative researchers call this **theoretical saturation**. The reference curve for this trace set:

```text
traces reviewed  distinct modes
             10    1  #
             20    1  #
             30    1  #
             40    1  #
             50    1  #
             60    1  #
             70    1  #
             80    1  #
             90    1  #
            100    1  #

last new mode appeared at trace 10; 90 traces since then without a new mode
```

The curve looks saturated early, and that is the trap. With 3 failures in 100 traces, a flat curve mostly says that
failures are rare, not that you have seen every kind. A reviewer who stopped after 9 traces would have seen no
failure at all; one who stopped at 30 would have seen 1 of the 3. A mode that occurs in 1 trace in 100 can easily be
absent from a 100-trace sample. In a random review order (exercise 5), the first *fabricated-evidence* trace turns
up anywhere from trace 6 to trace 19. Rare, severe modes show up late. Two rules of thumb follow:

- Read **at least 100 traces** on a first pass (the number Husain and Shankar recommend), spread across the kinds of
  question you get. When failures are as rare as here, read more, or read traces chosen to be hard (module 4).
- Then keep going until **about 20 consecutive traces** add no new mode and change no definition.

Saturation is not permanent. A new prompt, model, tool, or user group brings new failures. Repeat the analysis after
every significant change; it gets faster each time because the definitions exist.

## Who should label?

One person who knows the domain should own the verdicts and the definitions: Husain calls this role the
**benevolent dictator**. For MediaDoctor that is someone who can tell whether `c2.android.av1.decoder` at
1920x1080 and 30 fps really explains a 4K stutter, which a general annotator cannot. One owner keeps the
definitions consistent; others can review traces, argue about definitions, and flag disagreements, but one person
decides.

Avoid two common substitutes. **Crowd or generalist annotators** can check format but not whether an API level is
right. **An LLM labelling on its own** has the same blind spots as the agent it is judging, and you have no way to
know its error rate yet. Module 5 builds LLM judges and measures them against the expert's labels; that is only
possible because the expert's labels exist.

## Automatic signals: a reading aid, not a label

The lab's `signals` command flags traces using cheap checks from module 2: tool errors, citations without a
successful tool call, no tool calls, repeated retrievals, step budget, retrieval misses, and format. On this set:

| | Traces |
|---|---|
| Flagged by at least one signal | 1 (`m3t080`, `format`) |
| Failing traces with **no** signal | 3 (all three *fabricated-evidence* traces) |
| Flagged but passing | 1 (`m3t080`: its next-step line reads `Next step (standard Media3 recovery, not shown in the log):`, which the format check does not accept; the reference passes it) |

Signals are useful for choosing what to read first, and several will become evaluators. On this set they find
none of the 3 failures and raise one false alarm. Each signal checks something cheap and structural (did a tool
fail, is a citation backed by a call, is the format right); the failures here are structurally perfect answers with
one unsupported sentence. Only reading finds those.

## Checklist

- [ ] At least 100 traces reviewed, pass or fail each, in a fixed order
- [ ] A specific note on every failure, naming the first upstream step
- [ ] Failure modes with one-sentence definitions, severity, and fixability
- [ ] Every failing trace coded with at least one mode; definitions updated as they drifted
- [ ] A ranked list and a Pareto chart, with the priority rule written down
- [ ] Saturation reached: about 20 traces in a row with nothing new
- [ ] One named owner for the labels

## Summary

Error analysis is triage: look at the traces, write down what went wrong in plain words, group the notes into
failure modes that come from your data, count them, and fix what matters most. Label the first upstream failure,
keep tool errors that recovered separate from those that did not, and ask of every retrieval miss whether a better
query would have helped. Rank by frequency and severity, use fixability to find quick wins, and keep reading until
nothing new appears. One domain expert owns the result.
