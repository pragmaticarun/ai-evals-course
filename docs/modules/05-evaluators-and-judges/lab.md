# Lab 5: Code checks and three validated judges (offline)

**Time:** about 5 hours, half of it labelling and reading. **Needs:** the setup from [lab 1](../01-why-evals/lab.md),
and modules 3 and 4. **Does not need:** an API key or network access.

You will label MediaDoctor traces, run three code checks and three LLM judges against your labels and the
reference labels, iterate on one judge using the dev split, report every judge once on the test split, and produce
a corrected pass rate with a bootstrap interval. Keep your own files under `runs/`, which git ignores.

!!! info "Synthetic data, generated by Claude subagents"
    The data is synthetic: the agent turns were generated by Claude subagents and recorded through the real code
    paths, and the reference labels were written by Claude Opus annotators. The agent fails rarely (3 of 147
    traces, none in dev or test), so many of the numbers below are counts of zero; the lab says what each one can
    and cannot tell you. Section 10 shows how to run the judges on Claude with a key.

## 1. Update and check

```bash
git pull
uv sync
uv run pytest -q
```

## 2. The labelled trace set

```bash
uv run mediadoctor-lab05 labels
```

```text
train  89 traces,  3 failing   assumed-unstated-detail 1, fabricated-evidence 1, redundant-steps 1
dev    30 traces,  0 failing
test   28 traces,  0 failing
```

These are 147 runs of MediaDoctor on the dataset v1 queries that match a module 3 scenario. The splits are dataset
v1's, so a query's split never changes between modules. Only three traces fail, all in train, and none of them in
a mode one of the three judges checks. Dev and test have no failures, so every judge's TNR below is 0/0.

## 3. Label the traces yourself (about 2 hours)

Write the traces to a file and label them with the module 3 annotation tool:

```bash
uv run python -c "
from evalkit.synth import write_jsonl
from mediadoctor.lab05 import run_traces
write_jsonl('runs/m5_traces.jsonl', run_traces())"
uv run mediadoctor-lab03 annotate --traces runs/m5_traces.jsonl --labels runs/m5_labels.csv --annotator "your name"
```

Label at least the 30 dev traces and the 28 test traces, ideally all 147. Use module 3's mode names where they fit
and module 4's two new ones (`accepted-false-premise`, `assumed-unstated-detail`). Then compare:

```bash
uv run mediadoctor-lab03 compare --labels runs/m5_labels.csv --reference data/labels/module05_reference.csv
```

Where you disagree with the reference, decide who is right and write it down. Your labels are the ground truth for
*your* judges; the reference is one expert's opinion. If you find failures the reference missed, they are the
most valuable labels in this lab: they are the only way your judges' TNR gets measured.

Read the three check functions in `labs/mediadoctor/src/mediadoctor/lab05.py`. Code checks can run on all splits:

## 6. Iterate on the dev split

Run tool-grounding v1 on dev and read every disagreement:

```bash
uv run mediadoctor-lab05 judge tool-grounding --version v1 --split dev
uv run mediadoctor-lab05 disagreements tool-grounding --version v1 --split dev
```

Sort them: judge wrong, label wrong, or criterion unclear? Then compare `tool-grounding.v1.toml` with
`tool-grounding.v2.toml` (`diff config/judges/tool-grounding.v1.toml config/judges/tool-grounding.v2.toml`) and run
v2:

```bash
uv run mediadoctor-lab05 disagreements tool-grounding --version v2 --split dev
```

Both versions pass all 30 dev traces (TPR 1.00, TNR 0/0), so there are no disagreements to sort. Read the v2
change against the comment at the top of `tool-grounding.v2.toml`: what kind of dev disagreement would have led
to it, and which few-shot example would you want that train does not offer? Do the same for the other two judges
on dev:

```bash
uv run mediadoctor-lab05 disagreements false-premise
uv run mediadoctor-lab05 disagreements next-step
```

Neither prints a disagreement. Exercise 5 asks what the false-premise judge's clean dev result rests on. Write in
`runs/m5_notes.md` which failing traces you would need before a v2 is worth writing, but do not run anything on
test.

## 7. Report on the test split, once

When you have stopped changing the judges:

```bash
uv run mediadoctor-lab05 validate --split dev  > runs/m5_validation.txt
uv run mediadoctor-lab05 validate --split test >> runs/m5_validation.txt
uv run mediadoctor-lab05 checks >> runs/m5_validation.txt
```

```text
tool-grounding@v2      test  n=28 (human pass 28, fail 0)  TPR 1.00 (28/28)  TNR nan (0/0)  agreement 1.00
false-premise@v1       test  n=28 (human pass 28, fail 0)  TPR 1.00 (28/28)  TNR nan (0/0)  agreement 1.00
next-step@v1           test  n=28 (human pass 28, fail 0)  TPR 1.00 (28/28)  TNR nan (0/0)  agreement 1.00
```

This file is your judge validation report. Add one line per judge saying whether you would use it, and for what:
gating a release, a dashboard trend, or only pointing reviewers at traces. With TNR unmeasured, be explicit that
no judge here has shown it can catch a failure, and say how many labelled failures you would want first. Then try running v1 on test:

```bash
uv run mediadoctor-lab05 judge tool-grounding --version v1 --split test
```

It fails with a missing fixture: v1 was never run on test, by design. Once you have looked at test results, any
further change to a judge needs a fresh test set.

To validate against *your* labels instead of the reference (label every dev trace first), point the code at your file:

```bash
uv run python -c "
from mediadoctor import lab05
mine = lab05.annotations('runs/m5_labels.csv')
v = lab05.validate('tool-grounding', None, 'dev')
from evalkit.judge import confusion
print(confusion(lab05.human_pass('ignored-tool-output', list(v.verdicts), mine), {k: x.passed for k, x in v.verdicts.items()}))"
```

## 8. Corrected pass rate with a confidence interval

```bash
uv run mediadoctor-lab05 estimate
```

The judge has not seen module 3's traces before; we treat them as new traffic. On this data the command stops
with an error instead of printing an estimate: the judge passes all 100 module 3 traces, and the test split it
would take TPR and TNR from has no labelled failures, so TNR is 0/0 and the correction is undefined. (The error is
currently an `IndexError` from the bootstrap, which finds no resample where the correction is defined.) The same
happens to `uv run mediadoctor-lab05 ppi`, which prints a Rogan-Gladen row.

Answer in your notes, using exercise 3's hypothetical judge (TPR 0.90, TNR 0.60, observed 0.82): why is the
corrected rate higher than the observed one? (Hint: which is larger, the share of good answers the judge fails,
or the share of bad answers it passes?) Why is its interval so wide, and what would you do about it? And for the
course data: how many labelled failures would you need before `estimate` can say anything?

## 9. Compare with a 1 to 5 judge

```bash
uv run mediadoctor-lab05 likert --split dev
uv run mediadoctor-lab05 likert --split test
```

The table shows how scores spread over human PASS and FAIL. Here the FAIL column is all zeros, and the PASS
column moves between splits: 1, 13, and 16 traces at scores 3, 4, and 5 on dev; 0, 5, and 23 on test. Pick a
threshold on dev, then look at what it does on test, next to the binary judge. Exercise 2 asks you to make the
argument with numbers, and to say what they cannot show.

## 10. Optional: run the judges on Claude

With an API key, record real judge outputs for your own labels and compare:

```bash
EVALS_LLM_MODE=live uv run mediadoctor-lab05 validate --split dev
```

Judge requests are small: 2,000 to 5,000 input tokens with the few-shot examples, under 200 output tokens. At Haiku
prices the three judges on the dev split cost a few cents. The recorded judge outputs replay what was recorded;
live runs will differ, and on your own labels, especially ones with failures, expect the first prompt to need a
round of the dev-split loop above.
