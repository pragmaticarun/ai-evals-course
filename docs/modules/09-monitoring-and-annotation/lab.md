# Lab 9: A week in production, and a review app (offline)

**Time:** about 4 hours. **Needs:** the setup from [lab 1](../01-why-evals/lab.md), and modules 3, 5, and 6. A
browser for the app. **Does not need:** an API key.

You will replay a simulated week of MediaDoctor traffic, find the drift event in it from the monitoring output,
build a review queue, review traces in the annotation app, measure your agreement with a second annotator, and turn
your labels into a new failure mode and golden-dataset candidates. Keep your own files under `runs/`, which git
ignores.

!!! info "Synthetic traffic, generated by Claude subagents"
    The week's traffic and feedback are generated by `scripts/author_module09_fixtures.py` from documented rules, and
    the 40 AV1 cases are labelled `"source": "synthetic-authored"`. The traces the requests replay are module 3's
    recorded traces plus 40 recorded for this module; the agent's turns in them were generated by Claude subagents,
    and the reference labels and annotators A and B's labels by Claude Opus annotators. Every number the lab prints
    is computed from those files.

    The regenerated agent fails rarely: 4 of the 140 distinct traces (25 of 766 requests) fail, all with
    `fabricated-evidence`. The drift events are still in the data; this week they are drift without failure, and
    several steps below ask you to notice what that means for each tool.

## 3. Monitor

```bash
uv run mediadoctor-lab09 monitor
```

Read the output top to bottom before reading on, and write down three things: when something changed, what changed,
and who it affects. Then check against this reading:

- the daily table: Monday to Wednesday are steady; from Thursday the AV1 share, the topic PSI, the app 4.2 share, and
  the tool-error rate all rise (tool errors from none before Thursday to 6.9% on Thursday and 29 to 33% a day
  after), and `vela-v2` appears as a new device.
  The evidence-failure column stays at 0.0% all week;
- the p-chart for `evidence_fail`: flat at zero, with limits of [0.0%, 0.0%], because the check never failed in the
  reference window. Try `uv run python -c "from mediadoctor import lab09; print(lab09.chart('tool_error'))"`: the
  same zero reference rate, and every day from Thursday above it;
- CUSUM: `tool_error` alarms Thursday 18:36 IST, 8.6 hours after the rollout started (its p0 is the lab's floor of
  0.5%, since no tool errors happened before); `evidence_fail` and thumbs-down never;
- the snapshot change on Tuesday: 0/123 to 0/115, p = 1.00, nothing to see (and nothing there, though zero failures
  in 115 requests cannot rule out a rate up to about 2.6%);
- by app version after the rollout: 4.1.3 looks like the reference week; 4.2.0 has tool errors on 35.7% of requests.

Then open two or three of the 4.2.0 traces with a tool error (`grep vela-v2 runs/m9/traces.jsonl`, or wait for the
app in step 6) and decide whether the alarm is a failure. It is not: `codec_caps` has no profile for the `vela-v2`,
and the agent says so. Drift tells you where to look, not what you will find.

`--json runs/m9/dashboard.json` writes the same numbers for the app's dashboard page.

Two more views:

## 4. The online judge

```bash
uv run mediadoctor-lab09 judge
```

The judge ran on a 30% random sample. Compare the raw rates before and after the rollout with the simulation's truth
column: the judge passes every trace it applies to on both sides (1.000), and so does the truth. Then read the
validation line: module 5's test split has 28 labelled traces and all of them pass, so the judge's TNR is undefined
and there is no corrected rate or interval to print. Write two sentences: why an unchanged raw rate across the rollout
does not mean nothing changed (what is this judge's criterion, and what did change?), and why a corrected rate needs
failing labels. The last line shows the judge passing all 39 AV1 traces it applies to; what would you label to
measure its TNR on the new traffic?

## 5. Build the queue

```bash
uv run mediadoctor-lab09 sample --limit 60
```

Each line is a queue item: the request, how many identical requests it stands for (`+7`), the day, and why it was
picked (`signal:...` or `stratum:...`, with random picks marked `random`). Notice the rhythm: two triggered items,
then one random or stratified item. From item 20 on, most triggered items are `signal:tool_error` on the `vela-v2`.
The queue is written to `runs/m9/queue.jsonl` with each item's inclusion probability.

Before reviewing anything, compare the queue's failure rate with the week's:

```bash
uv run python -c "from mediadoctor import lab09; print(lab09.queue_bias())"
```

Unweighted, the queue says 0.058; weighted by 1/p, 0.040; the truth is 0.033. Keep that in mind when someone shows you
a rate computed from reviewed traces. With only 25 failing requests in the week, the weighted rate's interval
(`lab09.queue_bias_intervals()`) is [0.010, 0.096]: the weights fix the bias, not the small sample.

## 6. Review in the app

```bash
uv run mediadoctor-lab09 annotate
```

This rebuilds the trace store, the queue (60 items), and the dashboard, then serves the app at
<http://127.0.0.1:8009>. Enter a name; your labels go to `runs/m9/labels/labels-<name>.csv`.

Press `?` for the keys. The ones you will use most:

| Key | Action |
|---|---|
| `p` / `f` | pass / fail |
| `1` to `9` | toggle a failure mode (also sets fail) |
| `m` | name a new failure mode (sets fail; Enter saves) |
| `n` | write a note (Escape leaves the box) |
| `g` | flag as a golden-dataset candidate |
| Enter or `s` | save and load the next trace |
| `j` / `k` | next / previous without saving |
| `t` | expand or collapse all tool outputs |
| `c` | show the raw attributes |

Label the first 40 items. Judge each trace by module 3's rules: one verdict for the whole answer, every mode that
applies, and a short note on the first thing that went wrong. Read the answer with its citation marks (green: the
evidence is in the trace; red: it is not), then the tool outputs.

From item 14 on you will meet many answers about the `vela-v2` after `codec_caps` failed with an unknown device.
Read each one for the failure the v2 taxonomy names `unknown-device-guess`: describing the phone's decoders anyway.
This week's agent does not do that; it says the profile is missing and suggests what to check on the device, so these
are passes. If you do find a trace where no v1 mode fits, press `m` and name the new mode (the app adds it to the
mode list after the first use, in `runs/m9/labels/modes-added.toml`). The failures in the first 40 are subtler:
three correct answers that add a detail about a device no tool was asked about. Check every claim in the answer
against the tool outputs, not just the main one, and decide whether such an aside is `fabricated-evidence`.

Then look at the other pages:

- `/` shows your progress through the queue;
- `/dashboard` is the monitoring summary from step 3;
- `/agreement` compares you with annotator B, whose labels on the same 40 traces ship with the lab;
- the export links download your labels, the taxonomy CSV (modes ranked by count and severity), golden candidates
  as JSONL, and your golden flags.

The app also runs on any trace store in the course's format, with no lab code involved:

```bash
uv run annotate serve --traces runs/m9/traces.jsonl --queue runs/m9/queue.jsonl \
    --modes data/labels/production_modes_v2.toml --out runs/m9/labels-v2 \
    --dashboard runs/m9/dashboard.json --compare b=data/labels/module09_annotator_b.csv
```

## 7. Agreement and scoring

```bash
uv run mediadoctor-lab09 agreement runs/m9/labels/labels-<name>.csv data/labels/module09_annotator_b.csv
uv run mediadoctor-lab09 score runs/m9/labels/labels-<name>.csv
```

The first prints kappa on verdicts and per mode, with counts, and the traces you disagree on. The second compares
your verdicts with the reference labels. For reference, annotator A (also shipped) agrees with B on all 40 verdicts
and on the one `fabricated-evidence` tag (kappa 1.00), but `score` on A's labels gives 38 of 40 against the reference
(kappa 0.48: failures are rare, so a single disagreement costs a lot). Both annotators pass `r0031` and `r0634`, which
the reference fails for an unsupported aside. Pick the traces where you disagree with B or with the reference and
write which definition in the taxonomy caused it, and the sentence you would add to fix it.

## 8. Close the loop

```bash
uv run mediadoctor-lab09 close-loop runs/m9/labels/labels-<name>.csv \
    --flagged runs/m9/labels/golden-<name>.json --out runs/m9/candidates.jsonl
```

Each candidate is one distinct question that failed (or that you flagged), with its modes, a proposed split, and its
most similar existing golden question if that is close. Decide on each near-duplicate: keep, merge, or drop. Annotator
A's labels give a single candidate (`r0201`, proposed for dev, no near-duplicate); if you flagged some `vela-v2`
traces with `g`, they appear too, as coverage for the new device.

Read `data/labels/production_modes_v2.toml`, which adds `unknown-device-guess` with a definition, a severity, and a
detector, and decide whether any trace you reviewed has it. Exercise 5 writes the detector and runs it on all
traffic.
