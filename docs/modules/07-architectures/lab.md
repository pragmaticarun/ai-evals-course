# Lab 7: Evaluating each architecture (offline)

**Time:** about 5 hours. **Needs:** the setup from [lab 1](../01-why-evals/lab.md), and modules 5 and 6.
**Does not need:** an API key or network access.

You will measure retrieval over a new knowledge base, attribute RAG failures to retrieval or generation, run a
simulated user against two chat prompts, score agent runs as trajectories, build a transition-failure matrix for a
planner-and-specialists version of MediaDoctor, and validate vision judges on video frames. Everything replays from
fixtures. Keep your own files under `runs/`, which git ignores.

!!! info "Synthetic data: model outputs generated by Claude subagents"
    Every model output in this lab (RAG answers, chat turns, simulated users, planner and specialist turns, judge
    verdicts, and vision answers) was generated by Claude subagents and recorded through the lab's real code paths,
    in the exact Messages API format. Records are labelled `"source": "subagent-authored"`. The reference labels for
    RAG answers, sessions, and agent runs were written by Claude Opus annotators. The image labels come from the
    recipe that made each image. The retrieval results are computed live from `data/kb_v2/` and the relevance
    labels. The agents fail rarely, so several parts below show what the method finds on a system that mostly
    works. Section 9 shows how to record your own runs.

Each system answers all 48 queries from its top 3 passages (`rag.RAG_SYSTEM`). Read the four attribution cells as in
the lesson, then open a few answers of each kind:

```python
from mediadoctor import lab07

for run_id in ("baseline:r04", "improved:r04", "baseline:r34"):
    r = lab07.rag_runs()[run_id]
    print(run_id, "hit" if r.hit else "miss", lab07.rag_labels()[run_id]["note"])
    print("   context:", [c.id for c in r.context])
    print("   ", r.answer.replace("\n", " | "))
    print("   citations:", lab07.citation_checks(r))
    print("   faithfulness judge:", lab07.rag_verdicts("faithfulness")[run_id].critique)
```

`baseline:r04` is the lesson's worked example: retrieval missed, and the generator declined to guess.
`baseline:r34` is the only answer the labels mark unfaithful. It says "Android shares the speaker through audio
focus", which comes from a passage that was not retrieved, and the faithfulness judge passed it, claiming the
passage supports it.

Three things to notice. Every failure here is a retrieval failure: with an answering passage in the context, the
generator passed every time. The citation check separates *valid* (the id was in the context) from *supports* (the
cited passage is relevant); `baseline:r04` cites validly and still leans on a passage that does not answer the
question. And neither judge is validated yet. The faithfulness judge missed the only unfaithful answer (TNR 0/1, so
TNR is not measured). The answer-relevance judge failed 14 answers the labels call relevant, all of them faithful
abstentions. Before you use either to compare systems, get more negative examples and settle the criterion.

"Resolved" is a code check (the final answer names the cause), and it disagrees with the labels on 4 sessions; the
labels say v1 resolved 13 and v2 all 16. The simulator checks print nothing: no session was flagged, and the labels
record no simulator fault.

The scenarios are in `data/sessions/module07_chat.json`: an opening message, the facts the user knows, which of
them the opening already gives, and which a diagnosis needs. Read the two prompts (`chat.CHAT_V1`, `chat.CHAT_V2`)
and the simulator's instructions (`chat.USER_SYSTEM`), then read sessions:

```bash
uv run mediadoctor-lab07 session c05-v1    # answers at once with a list of causes: code says resolved, label says gave up
uv run mediadoctor-lab07 session c05-v2    # the same scenario with v2: asks for the start times, then diagnoses
uv run mediadoctor-lab07 session c16-v2    # a correct diagnosis the resolved regex does not recognise
uv run mediadoctor-lab07 session c04-v2    # the opening already had the box order, and v2 answers without asking
```

The turn checks (`chat.turn_checks`) are keyword heuristics: which facts a question asks about, and whether the user
had already given them. Heuristics like these need the same validation as a judge; the test suite checks them
against the labels for all 32 sessions, and exercise 2 compares a regex with the session-level judge.

No new fixtures here: the same 147 traces from module 5, read as trajectories against dataset v1's


```text
Planner + specialists on 47 dev and test queries: pass 45/47 = 0.96 [0.86, 0.99]

last ok \ failed        answer

step efficiency, passed runs: mean 0.94 (n=45, below 1.0: 9)

```

The reference trajectory for each query is in `data/labels/module07_agents.csv` (expected route and tools, from the
module 3 scenarios, plus the outcome label). `lab07.states` turns a run into states and decides which succeeded:
the plan matches the expected route; each brief contains every file, device, and log name from the question; each
tool call ran without an error; the expected evidence was gathered; the answer passed. Step through one of the two
failures:

```bash
uv run mediadoctor-lab07 run m4q028
```

```text
[plan    ] planner    {"route": ["knowledge"]} ...
[handoff ] planner   knowledge {"to": "knowledge"} Question from an Android engineer: how should the player handle audio focus ...
[tool    ] knowledge search_kb {"k": 3, "query": "audio focus phone call AudioFocusRequest AudioAttributes ..."} ...
[findings] knowledge   Findings: The KB's only relevant note says an app that "never requests focus, or ignores focus loss, ...
[answer  ] planner     Likely cause: Per the KB, an app that never requests focus, or ignores focus loss, keeps playing ...

states: [('plan', True), ('handoff', True), ('search_kb', True), ('evidence', True), ('answer', False)]
first failure: ('evidence', 'answer'); model calls 4, minimal 4
```

Every state up to the evidence succeeded, so the failure is in synthesis. If an earlier state had failed, only that
first failure would be counted, because fixing it is what changes the outcome. Then step through a passing run that
deviated from the reference (`uv run mediadoctor-lab07 run m4q163`: the planner routed to the device specialist
only, ffprobe was never called, and the label is still pass). Read the `note` column in the labels file for each,
and decide whether to fix the run or the reference.

Open the images in `data/media/frames/` (any image viewer) next to `data/labels/module07_images.csv` and judge a
few yourself before reading the judge's verdicts. The mild cases are the hard ones for people: the 100 ms dropout
is a thin line in the spectrogram. The judges caught every artifact, so here the false alarms are the thing to
read: the blocking judge flags every banded frame.

The judge specs reuse module 5's format (`config/judges/frame-blocking.v1.toml`, `frame-banding.v1.toml`) with a
vision prompt (`vision.VISION_JUDGE_SYSTEM`). Look at what a request contains and what the fixture stores:

```python
import json

from evalkit.fixtures import compact_request
from mediadoctor import lab07, vision

req = vision.judge_request(lab07.spec("frame-blocking"), "blocking_mild_testsrc.png")
print(len(json.dumps(req)), "bytes sent")
print(json.dumps(compact_request(req)["messages"][0]["content"][0], indent=1))
```

To regenerate the images (needs FFmpeg): `bash scripts/make_module07_images.sh`. The script is deterministic on one
FFmpeg build, but a different FFmpeg or x264 version can change a few bytes, which changes the fixture keys; the
images are committed so you never need to.

## 9. Optional: record real runs

With an API key, any part can be recorded live (`EVALS_LLM_MODE=record`). For example, the RAG answers and both
judges on them:

```bash
EVALS_LLM_MODE=record uv run python -c "
from mediadoctor import lab07
lab07.rag_runs()
lab07.rag_verdicts('faithfulness')
"
```

That is 96 Sonnet calls of about 600 input tokens plus 96 Haiku judge calls, well under a dollar at the prices in
`config/models.toml`. Recording overwrites the recorded subagent-authored records with the same keys; `git checkout fixtures/`
restores them. Real outputs need real labels: label at least the disagreements with the old labels before reading the
numbers. The chat sessions are the most expensive part (each turn re-sends the conversation), and a real simulated
user will produce new transcripts, so its sessions need new labels too.
