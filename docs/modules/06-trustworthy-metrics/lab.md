## 2. A tour of `evalkit.stats`

Open `labs/evalkit/src/evalkit/stats.py`; it is plain Python, under 400 lines with docstrings. Then try it:

```python
from evalkit import stats

print(stats.wilson_interval(49, 60))  # (0.70..., 0.89...)
print(stats.n_two_proportions(0.80, 0.85))  # 906 per variant
print(stats.mcnemar_exact(3, 3))  # 1.0: 3 vs 3 discordant queries is a perfectly even split
print(stats.pass_hat_k(5, 3, 2))  # 0.3: both of 2 runs pass, given 3 of 5 passed
```

Read `tests/test_stats.py` too: each function is checked against a hand calculation, and the Wilson interval
against simulated coverage (about 95% of intervals contain the true rate).

## 5. Intervals on module 5's numbers

```bash
uv run mediadoctor-lab06 judges
```

This prints each module 5 judge's TPR and TNR on the dev and test splits with Wilson intervals, then module 5's
corrected tool-grounding estimate. On the current labels every judge passes every labelled trace, and there are no
labelled failures at all: TPR is 1.00 [0.89, 1.00] on the 30 dev traces and 1.00 [0.88, 1.00] on the 28 test traces,
and TNR has n = 0. A TNR from zero failures is not a number, and neither is a correction that divides by
TPR + TNR − 1, so on this data the command stops with an error (a division by zero for the TNR) before it prints
a line.

Write down, for one judge, how many labelled *failures* would bring its TNR interval to ±0.10 (use
`stats.n_for_halfwidth`); at a 3% failure rate, work out how many traces you would have to label to find them. The
correction itself moved from `evalkit.judge` to `evalkit.stats` unchanged, and `evalkit.judge` re-exports it.

## 6. Compare the prompts, paired

```bash
uv run mediadoctor-lab06 compare
uv run mediadoctor-lab06 compare --mode accepted-false-premise
```

```text
v1: 0.98 [0.94, 0.99]   v2: 0.98 [0.94, 0.99]   (Wilson)
paired (v2 - v1): n=147  A 0.980  B 0.980  diff +0.000 95% CI [-0.034, +0.034]  discordant: only A 3, only B 3  McNemar p=1.000

v1: 1.00 [0.97, 1.00]   v2: 1.00 [0.97, 1.00]   (Wilson)
paired (v2 - v1): n=147  A 1.000  B 1.000  diff +0.000 95% CI [+0.000, +0.000]  discordant: only A 0, only B 0  McNemar p=1.000
```

(With `--mode`, "pass" means "free of that failure mode".) Overall, the two prompts fail on different queries (3
each) and the difference is zero. For the failure mode v2 was written to fix, there is nothing to fix: neither
prompt accepted a false premise on any of the 147 queries. Note the [+0.000, +0.000] interval: with no discordant
queries the bootstrap has nothing to resample, which says "no data", not "certainly no difference".

## 9. Sample sizes

```bash
uv run mediadoctor-lab06 samples
```

```text
v1 pass rate 0.98 on 147 queries; v1/v2 discordant share 0.04
queries for a +/-5-point interval on one rate: 31
```

Near a pass rate of 1, one rate is cheap to pin down: ±5 points needs only 31 queries. Comparisons are another
matter, and on this data the command stops with an error after these two lines: a 5-point *improvement* on 0.98 is
impossible, and Connor's paired formula needs a discordant share larger than the change (here 4%, 6 of 147
queries, against 5 points). Work the numbers out yourself with `evalkit.stats`: a 5-point *drop*
(`n_two_proportions(0.98, 0.93)`) needs 269 queries per prompt on separate queries; with 147 queries no improvement
over 0.98 is detectable unpaired (`mdd_two_proportions` returns nan, since the rate can only rise 2 points), and
paired, `mdd_paired(147, 0.04)` is nan too. The honest summary: this set can catch a large regression, but it cannot
show that one rare-failure prompt beats another.

## 10. Vanity metrics

```bash
uv run mediadoctor-lab06 vanity
```

```text
v1 helpfulness: mean 7.14 [6.98, 7.29]; passing answers 7.12, failing answers 8.00; separation (AUC) 0.22
v2 helpfulness: mean 7.16 [7.01, 7.31]; passing answers 7.18, failing answers 6.33; separation (AUC) 0.81
v1 token F1 vs reference answer: passing 0.37, failing 0.43; separation (AUC) 0.28
```

Separation is the chance that a random passing answer scores above a random failing one: 0.5 is a coin, 1.0 is
perfect. The same helpfulness judge scores worse than a coin on v1 and well above it on v2, because each AUC rests
on three failing answers. Exercise 5 looks at what that means for testing a metric.

## 12. Optional: record real repeated runs

With an API key, `run_traces` records any run you ask for; trial numbers keep repeats apart:

```bash
EVALS_LLM_MODE=record uv run python -c "
from mediadoctor import lab06
for run in (2, 3):
    lab06.run_traces('v2', run)
"
```

Each agent run makes two to four Claude calls of a few thousand input tokens; 30 queries times two runs is roughly
120 Sonnet calls, a dollar or two at the prices in `config/models.toml`. Recording overwrites the recorded records
for those runs; `git checkout fixtures/` restores them. Real runs need labels: run the module 5 judges on them, correct their
pass rates, and compare the run-to-run spread with the recorded one.
