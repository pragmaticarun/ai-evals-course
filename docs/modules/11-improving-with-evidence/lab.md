# Lab 11: Experiments on accuracy, latency, and cost (offline)

**Time:** about 3.5 hours. **Needs:** the setup from [lab 1](../01-why-evals/lab.md), and modules 3, 5, 6, and 8.
**Does not need:** an API key (section 12 is optional and does).

You will rank MediaDoctor's failure modes by the expected value of fixing them, read a pre-registration, replay seven
configurations (two prompt fixes, Haiku alone, a Haiku-to-Sonnet cascade, a retry on a judge's FAIL, and prompt
caching) on 119 dev queries, compare each with its parent, plot the accuracy against cost frontier, write the
experiment log and a decision memo, and spend the one look at the held-out split. Keep your own files under
`runs/`, which git ignores.

!!! info "Synthetic data: model turns generated by Claude subagents, real everything else"
    The model's turns (agent answers and the self-check judge's verdicts) were generated by Claude subagents
    standing in for each configuration and recorded through the lab's real code paths; they are labelled
    `"source": "subagent-authored"`. Their token counts and latencies are recorded with them and are not
    measurements of Claude Sonnet 5.5 or Haiku 5.5 through the API: on your own system, the rates are what you
    measure. Each configuration was generated in its own run, so two configurations' answers to the same query are
    independent samples, not the same answer with one thing changed. The agent loop, tools, prompts, request bodies
    (including `cache_control`), checks, prices (`config/models.toml`), and statistics are real code. The reference
    labels in `data/labels/module11_reference.csv` were written by Claude Opus annotators: they find a failure mode
    in 16 of the 1,029 final answers (all "skipped investigation"), so the configurations barely differ in quality,
    and several sections below show what the method finds on a system that mostly works.

## 7. Experiment 2: prompt caching (v3-cache)

Caching does not change what the model sees, so it should not change a single answer. Check it directly:

```python
from mediadoctor import lab11

a, b = lab11.task_results("v3"), lab11.task_results("v3-cache")
print(sum(x.answer == y.answer for x, y in zip(a, b)), "of", len(a), "answers identical")
print("timed out under v3:", [r.case_id for r in lab11.run_rows("v3") if r.timed_out])
```

```text
0 of 119 answers identical
timed out under v3: ['m4q017', 'm4q078', 'm4q086', 'm4q096', 'm4q175', 'm4q185']
```

No answer is identical, because v3 and v3-cache were generated in separate runs (see the box at the top): the
recordings are two independent samples of the same prompt, not one sample replayed with and without a cache. On a
real API at temperature above zero you would see the same thing. The no-change rule catches it: 25 of 119 tasks
grade differently, the log reports "graded answers identical: NO", and v3-cache is rejected. That is the rule
working as written; what it tells you is that "no change" can only be checked against a run that controls for
sampling (temperature 0, or several runs of each), and the pre-registration should have said so.

Then read the cost: in `trace v3-cache m4q131` the first call writes the prefix (`cache_write.input_tokens = 1033`),
and every other call in the run reads it. Explain, in two sentences, why caching made v3's few-shot examples almost
free.

## 8. Experiment 3: model tiering (haiku, cascade)

```bash
uv run mediadoctor-lab11 report --only v3-cache haiku cascade
```

Both pass the non-inferiority rule: Haiku's paired CI against v3-cache is −0.025 to +0.084, the cascade's +0.017
to +0.101, both above the −5-point margin, at 96% and 78% lower cost per success. Neither is kept, though, because
the rule only keeps a change whose parent was kept, and v3-cache was rejected (section 7). Check what the router
did: list the tasks where the cascade and v3-cache disagree, with the reference label of each final answer.

```python
from collections import Counter

from mediadoctor import lab11

base = {r.case_id: r for r in lab11.run_rows("v3-cache")}
rows = lab11.run_rows("cascade")
labels = lab11.reference_labels()
lost = [r for r in rows if base[r.case_id].success and not r.success]
won = [r for r in rows if r.success and not base[r.case_id].success]
print("lost", len(lost), "won", len(won), Counter(labels[("cascade", r.case_id)] for r in won))
print("escalated:", sum(r.escalated for r in rows), "of", len(rows))
print("labelled failures:", Counter(labels[("haiku", r.case_id)] for r in rows), "(haiku alone)")
```

```text
lost 0 won 7 Counter({'none': 7})
escalated: 27 of 119
labelled failures: Counter({'none': 112, 'skipped': 7}) (haiku alone)
```

The cascade lost nothing and escalated 27 tasks, and the labels find no failure in any of its final answers, while
Haiku alone has 7 answers that skipped the investigation. The code-check router is good at exactly that mode: a
skipped investigation fails the `investigated` or `citations` check, and Sonnet's second attempt fixes it. On data
where Haiku's failures are well-formed, properly cited wrong diagnoses (an adopted false premise, an answer that
contradicts the tool output), the same router would pass them to the user; a router is only as good as its recall
on the failures that matter. Write the hypothesis for the experiment that would test that (a judge-based router,
on labelled data with those failures) in the experiment-log format.

## 11. The experiment log and the decision memo

```bash
uv run mediadoctor-lab11 log --out runs/m11/experiment_log.md
uv run mediadoctor-lab11 memo --out runs/m11/decision_memo.md
```

The log merges what was written before each run (`config/experiments/log.toml`) with what was measured, and applies
each experiment's rule. The memo applies the pre-registered decision rule: keep each change that passed its own test
(and whose parent was kept), recommend the most accurate kept configuration. On this data no change on the
v1 → v2 → v3 → v3-cache path passes, so the chain stops at v1, and the draft reads "Switch MediaDoctor from
**v1 (release)** to **v1 (release)**". Haiku and the cascade passed their own rules but sit under the rejected
v3-cache, and the memo's table lists them as "rejected" with their passing reason, which is misleading; its "How
sure we are" line also prints "about nan%" for the detectable difference, because the recommendation is the release
itself and no task changed outcome. Read the draft against the
[decision memo template](../../eval-templates/decision-memo.md) and edit it: say plainly that the recommendation is
to keep v1 and why, fix those two lines by hand, add the owner, and add one sentence on what would change your mind
(a validated grader). Keep it to one page. A generated memo is a draft, and this one shows why.

held-out result comes out clearly worse than dev, the right response is to find out why (an overfit prompt? a split
that differs?), not to look again until it passes.

## Optional: record a few live runs

With `ANTHROPIC_API_KEY` set (never commit it), you can replace the recorded model with the real one for a handful
of dev queries. This records into `runs/`, so the course fixtures stay untouched; ten v3-cache tasks cost a few cents.

```python
from functools import cache
from pathlib import Path

from evalkit import LLM
from mediadoctor import experiments as X
from mediadoctor import lab11

out = Path("runs/m11/live-fixtures")
X.llm_for = cache(lambda ns: LLM(namespace=ns, mode="record", fixtures_dir=out, source="live"))
for c in lab11.split_cases("dev")[:10]:
    t = X.run_task(c, "v3-cache")
    print(
        c["id"],
        "ok" if t.graded_success else "FAIL",
        f"{t.latency_ms / 1000:.1f}s",
        f"${t.usage.cost_usd:.5f}",
        "cache read",
        t.usage.cache_read_tokens,
    )
```

Compare the real latencies and cache reads with the replay's. Expect the first call to write the cache and later
ones to read it only if they arrive within five minutes and the prefix is byte-for-byte identical.
